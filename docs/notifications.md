# 状态栏通知设计

> 需求原文：「当存在逾期的事项或者今日有任何未完成事项（哪怕是还没到的），
> 都向安卓系统发送通知，常驻在状态栏显示有哪些事项。」

这份文档说明**为什么这样实现**，以及哪些部分是纯网页做不到的。

---

## 一、先划清边界：哪一部分网页做不到

| 能力 | 纯网页（PWA） | 原生前台服务 |
| --- | --- | --- |
| 页面打开时显示通知 | ✅ | ✅ |
| 页面切到后台仍能更新 | ✅（Service Worker 会被唤醒） | ✅ |
| 通知**不可划掉** | ❌ | ✅ |
| App 被划掉后仍在状态栏 | ❌ 没有任何 JS 在跑 | ✅ 系统保活 |
| 设备重启后自动恢复 | ❌ | ✅ |
| 后台分钟级精确刷新 | ❌ | ⚠️ 需要额外排期，本项目未做 |

结论：**网页能覆盖"应用在使用中"的全部场景，覆盖不了"应用被划掉之后"**。
后者只有前台服务能做到，于是有了 `app/` 这层极薄的原生外壳 —— 界面代码一行未改。

Web Push 是另一条能覆盖全部场景的路，但它需要一个推送服务器，
与本项目"不依赖自建后端"的架构约定冲突，故排除。

---

## 二、数据流

```
本地仓库（IndexedDB）
   │  subscribe：勾选 / 编辑 / 同步拉取都会推进 rev
   ▼
stores/tasks.collectNotifySource()        ← 逾期 + 今天全部（含未来）
   │
   ▼
domain/notifyPlan.buildNotificationPlan() ← 纯函数：排序、截断、生成文案
   │
   ▼
lib/notifyRuntime（防抖 800ms + 每 60s 对齐时钟 + 可见性/pageshow 触发）
   │
   ├── 浏览器 ──► Service Worker registration.showNotification()
   └── 原生壳 ──► NotifyPlugin.setNotification() ──► NotifyService（前台服务）
```

四个模块的职责刻意不重叠：

| 模块 | 只负责 | 不负责 |
| --- | --- | --- |
| `stores/tasks` | 从应用状态里取数 | 排序、文案 |
| `domain/notifyPlan` | 纯计算：排序、截断、标题 | 何时发、发到哪 |
| `lib/notifyChannel` | 送到哪个平台 | 内容、时机 |
| `lib/notifyRuntime` | 什么时候重算 | 内容、平台 |

这样切分的直接好处是：**通知里到底会出现什么，可以在单测里逐字断言**，
不需要真的弹一条通知；平台差异被压缩在一个 `NotifyChannel` 接口里。

## 三、内容口径

- **逾期**：所有未完成、结束时间已过去的实例（fixed 与 deadline 都在内）
- **今日**：今天剩下的**全部**未完成实例，包括还没到时间的
- 两者都空 → 通知被**撤销**，而不是显示「0 项」

标题两段式：`3 项逾期 · 今日还剩 5 项`（某一段为 0 时省略）。

正文每行一项 `HH:mm  标题`；没有可读时刻的全天事项只显示标题；
最多 `maxLines` 行（3–12，默认 8），超出归并成 `…还有 N 项`。
截断时保留**最紧急**的几项（逾期 → 进行中 → 还没到），但展示顺序仍按时间。

单行标题超过 40 字会截断 —— Android 通知每行只给一行多一点的宽度。

### 三处容易踩的坑

1. **跨夜任务会两边都漏。** 一条 23:00–01:00 的任务，在 00:00–01:00 之间
   既不算逾期（`endAt` 还没到），开始日又不是今天 —— 只按开始日枚举的话，
   它在这一个小时里**根本不出现**；若它是唯一一项，通知压根不会发。
   所以 `collectNotifySource` 把"昨天开始、今天结束"的实例（`overflowInto` 的语义）
   也并进今日。同时它又可能已经逾期，因此还要按
   `<taskId>|<occurrenceKey>` 去重。
2. **已完成的实例必须留在数据里。** 「今天还剩几项」是个减法，
   如果把已完成的提前过滤掉，分母就错了。
3. **全天事项要认 `allDay` 字段，不能靠形状猜。** 曾经用
   "00:00 且首尾同一时刻"判断全天，但用户完全可能在截止任务上**明确选** 00:00 ——
   那是个真实的可读时刻，按形状猜会把它悄悄吞掉。

## 四、投递时机

| 触发源 | 行为 |
| --- | --- |
| 本地仓库变更 | 防抖 800ms 后重算（连续编辑不该每敲一个字发一条） |
| 每分钟脉冲 | 重算一次，让「进行中 / 还没到」随时间自己变化 |
| 页面重新可见 | 立即重算（后台期间定时器可能整段没跑） |
| `pageshow` | 同上，覆盖"从返回缓存恢复"这一路径 |

**浏览器里页面可见时默认不发**（用户正开着 App 就别再响）；
**壳内不看可见性** —— 常驻通知本来就该一直挂着，否则切回 App 它就消失，
反而像是被关掉了。

首次调用立即执行、不排队，实现方式是 `lastStamp = -Infinity`
而不是 `0`：测试里的假时钟就是从 0 开始的，用 0 会让"第一次"被当成"刚发过"。

## 五、原生侧为什么不自己算

`NotifyService` 不持有任何日程数据，它只接收一段已经渲染好的文本。
理由是重复规则展开、向量时钟合并这些逻辑都在网页里 ——
在原生侧重算等于把领域逻辑实现第二遍，两边一旦不一致就会显示过期内容。
原生侧只做三件事：申请权限、显示、撤销。

负载格式（与 `lib/notifyChannel.ts` 的 `NativeNotifyPlan` 一一对应）：

```json
{
  "id": 1,
  "tag": "twische.today",
  "title": "2 项逾期 · 今日还剩 3 项",
  "body": "09:00  晨会\n…还有 1 项",
  "count": 5,
  "active": true
}
```

原生侧把它拆成行，用 `BigTextStyle` 逐行渲染。

## 六、权限

- **浏览器**：`Notification.requestPermission()`。被拒绝后浏览器不会再弹框，
  设置页会引导用户去系统/浏览器设置里手动允许。
  页面重新获得焦点时会重新对一次权限，避免开关停留在旧状态。
- **"支持与否"不能用 Web Notification API 判断。** 安卓 WebView 至今没有实现
  Notifications API，壳内 `typeof Notification === 'undefined'` 恒成立。
  若据此判成"不支持"，整张通知卡片连开关都不会渲染 —— 壳内用户将没有任何入口。
  所以 `notificationEnv()` 先看平台：壳内一律交给原生通道回答。
- **Android 13+**：`POST_NOTIFICATIONS` 运行时权限，走 Capacitor 的权限别名机制。
  13 以下没有这个权限，直接视为已授予。
- **权限是异步读到的**，而调度器需要**同步**判断"现在能不能发"。
  折中：先用上一次的缓存值，同时异步刷新；刷新结果变化时回调通知调度器重算。

## 六点五、原生侧的两个硬约束（实现时踩到的）

**前台服务类型必须是 `specialUse`，不能是 `dataSync`。** 两条都来自 AOSP 行为：

1. Android 15 起，`BOOT_COMPLETED` 广播**不允许**启动 `dataSync` 类型的前台服务 ——
   `ActiveServices.shouldAllowBootCompletedStart()` 的白名单（`FGS_BOOT_COMPLETED_ALLOWLIST`）
   只含 `connectedDevice / health / remoteMessaging / systemExempted / specialUse / location`。
   用 `dataSync` 的话，重启后恢复通知会抛 `ForegroundServiceStartNotAllowedException`。
2. Android 15 起，`dataSync` 在后台累计满 6 小时会被判超时，系统回调 `Service.onTimeout()`，
   不在几秒内 `stopSelf()` 就是一次 `RemoteServiceException` 崩溃。
   而本服务的常态就是"一直挂着"，必然撞上。

即便如此，`onTimeout()` 仍然被覆写并降级为普通通知 —— 多一层保险。

**失败路径不能删数据。** 后台启动受限、额度用尽、服务被重建，这些失败大多是**可恢复**的。
所以除了"网页明确说没有事项了"这一条路径，其余失败都只撤通知、保留落盘负载 ——
否则下次开机 `restore()` 会因为没有负载而直接返回，通知静默消失，而且再也补不回来。

另外，`NotificationManager.notify()` 是 oneway 调用，**不会抛异常**（没权限时系统只丢弃并打日志）。
因此"发不出去"不能靠 `catch` 判断，必须显式查 `areNotificationsEnabled()`；
否则服务会停在一个"既不是前台、也没有通知"的状态里，还对外宣称成功。

## 七、明确没做的事

- **后台分钟级精确刷新**：网页被系统回收后，状态栏保留的是最后一次算出的内容。
  要做精确刷新需要在原生侧再实现一套排期（AlarmManager + 通知数据本地化）。
- **图标角标**：`Badging API` 只在部分平台生效，收益不稳定，暂不引入。
- **通知里的"完成"按钮**：`notificationclick` 只能唤起应用，
  而写入打卡需要向量时钟，因此按钮最终仍要回到应用里完成，交互上并不更快。
